# Protected browser recovery-history download

## Decision and acceptance
Expose the existing audited format-3 encrypted historical wallet/delivery pair through the ordinary wallet and merchant browser. A real Chromium download must decrypt and audit, preserving exact signed originals, receipts and unknown holds with no new signing/submission, source-journal mutation or key access. This is historical recovery data, not active restoration, renewed trust, latestness, device fencing, on-chain privacy or a complete account backup.

## Fixed scope and boundaries
POST /api/backup-history only. Preserve exact literal Host, Origin, Sec-Fetch-Site, CSRF, Content-Length/body caps, duplicate-key refusal, existing route allowlist and no-store/CSP/frame-denial/security headers. Exact fields: passphrase, repeat_passphrase, scope_confirmed. Require strings whose UTF-8 bytes are 16..1024 each, constant-time matching bytes and scope_confirmed is exactly True before opening the service or creating artifacts. No caller-selected formats, paths, endpoint, roles, policies, KDF/compression or journal selection.

Explicit consent says this captures all retained history from the shared wallet/delivery journal, including other roles and hidden generic decisions. Includes proofs, signed decisions, retained attempts/responses/receipts and unresolved obligations. Excludes private keys, vaults, invoice content and invoice/request/separate receipt books, derived ledger and current spending authority. The merchant adapter must delegate explicitly to desk.platform; no duck-typed audit facade.

The browser uses format 3, maximum 8 MiB ORIGINAL captured pair BLOB bytes and 16 MiB final encrypted output. Both caps tighten caller limits; original protocol/core caps remain unchanged. Oversize refuses the entire export; no trim/eviction. Explain the existing CLI format-3 fallback. Logical cap must be checked on the EXACT audited in-memory pair encrypted; a preflight on live DB followed by recapture is insufficient.

Implement additive optional max_capture_blob_bytes and max_backup_bytes keyword arguments to the canonical backup function. Require explicit format_version=3 when either is supplied; exact positive integer (bool refused), never exceeding the corresponding original format-3 hard bound. Defaults preserve every original format-1/2/3 selector behavior. Sum known snapshot BLOB columns with SQLite length from the captured pair, after original audit, before KDF/sealing. Original audit/capture locks/order remain unchanged. Use the caller physical ceiling in the existing atomic _publish_parts, preserving complete-file and partial-file cleanup behavior. No duplicate cryptography, changed recovery decoder, new key schema or relaxed checks.

Build complete encrypted output in a NEW owned private temp directory below the fixed workspace before headers. Validate output regular/private file and exact ciphertext length/hash; use a bounded file streaming loop and fixed attachment filename. Do not return JSON-embedded bytes, paths, passphrases or journals. If disconnected after headers close, clean only the owned directory; never append JSON to a binary reply. No persistent backup catalog/tokens, GET file endpoint, arbitrary file reader, automatic retries or background jobs. An explicit retry makes fresh encryption and no financial action. Cleanup guarantees file ownership, not memory zeroization or erasure of browser/OS/download data.

Make backup available even when existing evidence/policy is expired; original historical capture is appropriate, never enable signing or present backup as trusted current evidence. Existing startup still requires configured development vault files and other catalogs; no key-loss/disaster-startup claim.
