# Protocol 6 atomic treasury consensus design

## Authorized outcome and alternatives
Dom has authorized continued development and private-repository merges. This slice promotes the frozen atomic treasury relation into a separately pinned, fresh-genesis, four-validator development protocol. Existing P1-P5 and local labs remain byte-identical. It does not deploy a network, spend money, create Actions, touch DNS or other projects, or use real assets or production keys.

Embedding treasury commands in P5 would reinterpret an already pinned protocol. Driving the existing local SQLite ledger directly from ABCI would expose unsigned revocation and mix staged proposal state with durable state. A separate P6 deterministic state machine with a dedicated verifier-only bridge preserves both contracts and is selected.

## Contract
Canonical P6 genesis contains protocol version 6, chain ID, exact static equal-power four-validator roster, frozen treasury profile fingerprint, dedicated bridge binary SHA256, known-answer transaction SHA256 and the entire trusted initial treasury state. Every application requires exact expected genesis bytes; there is no unpinned launch. The proof's genesis field is an independently chosen treasury domain, not a digest of a genesis containing its own note commitments. This first runner uses the previously qualified public synthetic domain 700. Reusing that synthetic domain in another run is not distinct issuance or deployment privacy. AppHash and certificates bind the entire exact chain genesis, including validator roster and worker identity.

The frozen relation stays K14, 25 public fields, 3200 proof bytes, exactly 4008 transaction bytes. P6 has its own AppHash/transaction/receipt domains. Grant IDs, mission, epoch and fee are fixed at genesis. Only proof-authorized parent/grant spending commitments advance. No revocation, rotation, enrollment, minting, merchant redemption, wallet obligation release or snapshot installation API is supported.

CheckTx and proposal evaluation use isolated copies of committed state. Ordered execution requires exact current parent, selected grant and context root. Historical admitted value roots are allowed; historical authority roots are not. Each accepted proof atomically advances both allowance commitments, creates exactly two note commitments, records all three nullifiers, charges the fixed fee and writes an exact raw transaction receipt. Duplicate request commitments are rejected even with another valid proof. Failure leaves every treasury field unchanged.

Finite ceilings: 64 heights, 2 transactions per block, 8 candidates, 64 retained transactions, 16 notes, 7 successful payments and 256KiB canonical state. Full retained-history replay derives state and results on reopen. FinalizeBlock stages a deterministic response; Commit writes state and exact response/history together with FULL-sync SQLite WAL. Conflicting pending or committed finalize identities fail closed. Info/query expose committed state only. Engine next-validator hash and last-commit quorum are checked. State sync is explicitly refused.

The new verifier-only Rust bridge accepts only verify/context-root/note-root operations. Invalid proof is a typed normal result; profile failure, timeout, signal, binary mismatch and malformed response stop execution. A separate Python exec launcher supplies CPU/address-space/file-size/core/file-descriptor limits without preexec_fn in threaded ABCI. This is a bounded trusted-host subprocess, not the P5 seccomp worker or public-node isolation. Accepted exact proof bytes may be cached within a bounded eight-entry cache; current-state checks always run independently.

## Acceptance
Actual frozen proofs must pass initial and refreshed authority execution, both shared-parent orderings, duplicate request rejection, malformed/corrupt proof rejection, exclusive expiry and wrong domain. Proposal calls must not mutate state. Commit failures and process death before durable commit leave the old state; process death after commit preserves the whole new state and response. Reopen must reject altered state/results/genesis/schema. A real CometBFT 0.38.25 four-validator loopback scenario must commit a treasury payment, reject its stale competing proof, commit a refreshed second payment to exhaust the aggregate allowance, converge, survive same-store restart and produce an H+1 signature-authenticated full-state receipt. Certificates establish AS-OF state under the static quorum assumption, not freshness or production consensus security.
