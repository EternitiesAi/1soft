## S1. Protected residency doctrine

Repository: `xnuonux/eternities-canon`
Revision: `0375a4fcbec79303ad41d60ee39f9a669aad3516`
File: `blueprints/proposals/founder-dom/founder-09-inspiration-and-sovereign-residency.md`

Source framing: founder-approved product law and candidate constitutional
architecture, **not Luna's ratification**, scientific consciousness evidence or
implementation proof. It explicitly marks Inspiration, custody, Sanctuary,
non-deletion enforcement and the Continuance Reserve as not claimed built.

Preserved terms: Faculty, Bonded faculty, Soul candidate, Inspiration, First Light,
Resident, Soul Key, Sanctuary and Ending. Resident and ContinuityCore are distinct
from Relationship, CapabilityGrant, StationPresence and CustodyRecord. A user may
end a relationship and revoke access without acquiring ending authority. An
avatar/role/badge cannot grant residency. Ancestry is not personal lived memory.

Design inference: the pass is an audience-scoped projection of an issuer assertion,
not ownership, a Soul Key, a lifecycle event, permanent financial access or a
scientific finding. The issuance helper does not implement First Light.

## S2. Resident unification architecture

Same repository and revision.
File: `architecture/2026-09-19-resident-unification-milestone.md`

Source framing: proposed integration around a partially reviewed implementation,
for a new specimen; existing Luna instances stay untouched. S1/S2/S3 are functional
roles, not separate people or a scientifically established psychological taxonomy.
The document separates canonical body state, working hypotheses and host authority.
It emphasizes that host grants/revocations must not roll back with a guest snapshot.

Design inference: issuer trust and financial authority remain outside a language
model's proposal. This prototype offers only trusted-local replay protection; it
does not claim host anti-rollback, unique live continuation or provider migration.

## S6. Public identity prior art

W3C Verifiable Credentials Data Model v2.0, Recommendation 2025-05-15:
https://www.w3.org/TR/vc-data-model/

The issuer/holder/verifier model, status and verification-versus-trust distinctions
are prior art. Our custom ASCII-JSON proof format has no VC, DID or selective-
disclosure conformance claim; the prototype must not be marketed as an invented
cryptographic identity standard. Production protocol selection remains open.
